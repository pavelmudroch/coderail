Implement automatic remediation through `cr doctor --repair` and extend doctor
diagnostics to instruction metadata and ticket health.

## Intended outcome

- Replace the current `not implemented` error with useful automatic remediation.
- Deliver the agreed project initialization repairs, conservative instruction
  frontmatter repairs, ticket health checks and metadata-driven file moves.
- Follow up on the diagnostics delivered by [Doctor command](../doctor-command/IDEA.md).
  That idea intentionally deferred automatic repair; preserve its diagnostic
  contracts except where explicitly superseded here: implement --repair, allow
  instruction customization, and add instruction metadata and ticket checks.

## Current understanding

- `src/commands/doctor.ts` parses `--repair` but rejects it before diagnostics.
- Diagnostic findings use `DoctorFailure = { message: string; repairable: boolean;
  manualRepair: string[] }`. Actual checks currently mark all findings unrepairable;
  there is no repair action or stable finding identifier in the report.
- Installation checks cover global harness instructions, resources, distribution
  ownership, launcher, and PATH. Project checks cover initialization and local
  instructions; configuration and configured executable checks follow.
- `src/commands/init.ts` already creates a missing project config and repairs
  required ignore rules while preserving existing lines. Its default config
  generator is private. Calling init wholesale would also produce command output
  and use its current-working-directory behavior; shared logic may be preferable.
- `src/commands/install.ts` can restore harness instructions from installation
  resources. It protects modified files with `--force` and per-action confirmation,
  maintains ownership manifests, and rejects symlink destinations. Its installation
  helpers are private; its command entry point logs per-harness failures.
- Doctor runs before normal configuration/runtime startup, including when
  configuration is invalid. Repairs must account for that bootstrap context.
- Both harness translators already require nonblank string `name` and
  `description`, and require skill `name` to equal its directory name. Markdown
  subagent names match their filename stem. Installed Codex agents are TOML,
  whereas installed skills and Claude agents remain Markdown.
- Doctor currently checks instruction ownership checksums, not frontmatter
  validity. It treats modified installed files as failures, so supporting user
  customization requires revisiting diagnostics as well as repair behavior.
- The Markdown parser recognizes an opening `---` only at the beginning and
  requires a closing delimiter. Without the opener it treats everything as body;
  without the closer it throws. Repair needs explicit boundary detection rules.
- Doctor does not currently inspect tickets: it does not scan ticket files,
  validate their frontmatter, or check dependencies/status consistency.
- Ticket creation writes id, slug, title, status, timestamps, and dependencies.
  Filenames are `<id>-<slug>.md`, with slug generated by `Text.slugify(title)`.
  Current resolution derives id/slug from filenames without comparing metadata
  id/slug or enforcing the status directory, and throws on the first bad ticket.
  Doctor needs an independent inventory tolerant of individual malformed files.
- Current dependency satisfaction accepts a closed/done ticket, follows a
  closed/duplicate ticket's duplicate-of chain, and rejects dismissed or nonclosed
  tickets. A done ticket's historical dependencies are not traversed.
- `cr ticket close` itself does not require satisfied dependencies. Thus "stuck"
  should be defined in terms of dependency readiness/progression rather than a
  literal inability to invoke close; the agreed semantics are recorded below.

## Confirmed requirements and direction

- Repairing missing project configuration and required ignore rules is mandatory.
- Installed harness instructions must permit user modifications; content changes
  alone should not automatically be treated as errors or reverted.
- Skill frontmatter `name` must match the skill directory name.
- Include conservative skill frontmatter repair in asset instructions and
  installed harness instructions under the rules below.
- Doctor must also diagnose ticket metadata, placement, references, cycles, and
  tickets whose dependencies prevent normal progression, as described below.

## Required ticket checks

- Frontmatter is the source of truth for ticket identity and status. Derive the
  expected `<id>-<slug>.md` filename and open/active/closed directory from valid
  metadata; report the file location as wrong when they disagree. Do not rewrite
  metadata to match its current filename or directory.
- Check the title against its slug using the existing title-to-slug convention.
  Inconsistent metadata needs explicit handling rather than choosing authority
  from the current filename. Missing/invalid metadata cannot be inferred from it.
- Resolve dependency and duplicate references using frontmatter IDs, including
  when a referenced ticket has a mismatched filename or directory.
- Check closed reasons (done, dismissed, duplicate) and required duplicate-of
  information for duplicate closures.
- Check that dependency targets exist, and detect circular dependencies.
- Identify tickets stuck because their dependencies cannot be satisfied, including
  transitive effects. Distinguish these from ordinary pending dependencies.
- Automatic repair includes renaming/moving ticket files to match valid
  authoritative frontmatter under the conditions below.

## Agreed ticket dependency semantics

- Include duplicate-of target existence, self-references and duplicate-chain
  cycles; inspect dependencies and duplicate-of together when evaluating progress.
- Report duplicate ticket IDs, malformed frontmatter/fields and invalid filenames
  without letting one bad ticket hide independent findings.
- An open/active dependency by itself is normal waiting. Report an unfinished
  ticket as stuck when its required chain reaches a dismissed ticket, a missing
  or unusable target, or an unresolvable cycle; show the causal chain.
- Follow closed/duplicate targets until done, pending, or a blocker is reached.
  A done ticket satisfies an incoming dependency regardless of its own historical
  dependencies. Still diagnose historical reference/cycle integrity separately.
- Do not automatically close/reopen tickets, change reasons, remove dependency
  edges, or choose duplicate targets to resolve graph problems.

## Agreed ticket repair boundaries

- Allow `--repair` to rename/move a ticket to match valid authoritative frontmatter
  when its identity is unique and the destination is unoccupied, preserving file
  contents. Report conflicts or invalid metadata for manual correction.
- Metadata conflicts (including title/slug disagreement), duplicate IDs and
  dependency graph errors remain manual fixes unless separately agreed.

## Agreed execution contract

- Plain `cr doctor` only diagnoses; `cr doctor --repair` applies supported repairs
  without prompts, including with global `--non-interactive`.
- Collect findings first, attempt supported repairs, then rerun diagnostics.
- Continue independent repairs if an action fails. Report repaired and unresolved
  issues; exit 0 when no failures remain after repair, otherwise 1.
- Do not recursively repair new findings discovered by rechecking in the same
  invocation. Repeated invocations converge without rewriting healthy files.
- Preserve verbose-only progress/context on stderr and collected final results
  on Log.output. Include action descriptions and useful failure paths/chains.
  Report attempted action errors even when subsequent diagnostics clarify the
  final state; diagnostics determine the final exit status.

## Agreed frontmatter repair boundaries

- Check all asset skills and Markdown subagents. For installed harnesses, check
  only Coderail-owned instructions, in both global and local installations.
  Installed Codex agents are TOML and outside Markdown frontmatter repair.
- Correct or insert `name` in a parseable frontmatter block, preserving
  the body, description, and unrelated fields; do not regenerate instructions.
- Expected names are skill directory names and Markdown subagent filename stems.
- Restore a missing opening delimiter only when a leading metadata block and
  an existing closing delimiter can be identified: the file must start with
  parseable metadata containing a nonblank description, and already contain a
  closing delimiter. Preserve the body after that delimiter.
- Leave missing closing delimiters, both delimiters absent, malformed metadata,
  and missing/blank descriptions as manual fixes initially: body boundaries or
  intended content may be ambiguous.
- Preserve customized content and existing ownership checksums. Do not record
  user modifications or doctor repairs as pristine installation baselines.

## Agreed integrity and operational boundaries

- Extend the customization policy to compiled instruction Markdown
  assets: validate their content rather than fail solely for a checksum mismatch.
  Keep distribution checksums strict for binaries and other distribution files;
  missing owned instruction files and unreadable/unsupported entries still fail.
- Distribution recovery, shell PATH edits, and harness executable installation
  are outside this version.
- Repair actions are idempotent and revalidate their input before writing.
  If content changed since collection or a destination became occupied, report
  an action failure rather than overwrite newer work. Cancellation propagates,
  stops further actions, and leaves completed repairs in place, without rollback.
- Doctor never updates ownership checksums or manifests to absorb edits or
  repairs, in either installed harness instructions or distribution assets.
  Existing installer/uninstaller ownership semantics are unchanged.

## Agreed module boundaries and interfaces

Keep this as one idea; the checks share collection, action and recheck contracts.
No shared Command or harness connector API changes are needed.

- `src/commands/doctor.ts`: collect diagnostics, run deduplicated actions only
  with --repair, rerun all diagnostic phases once, and render results/exit status.
  Keep installation-before-project ordering on both diagnostic passes.
- `src/commands/doctor/types.ts`: preserve DoctorReport and existing failure
  fields; add optional `repair?: DoctorRepair` to DoctorFailure, with
  `DoctorRepair = { key: string; description: string;
  apply(signal: AbortSignal): Promise<void> }`. A finding is repairable exactly
  when it has an action. Stable keys deduplicate multiple findings sharing a fix.
- `src/commands/doctor/repairs.ts`: export
  `runRepairs(actions: DoctorRepair[], signal: AbortSignal):
  Promise<DoctorRepairResult[]>`, where results contain the key, description,
  and optional error message. Catch action errors independently, propagate
  cancellation, and leave verification to the subsequent diagnostics pass.
- `src/commands/doctor/tickets.ts`: export
  `Tickets.check(projectRoot: string, signal: AbortSignal): Promise<DoctorReport>`.
  Own tolerant inventory, frontmatter identity indexing, metadata and graph
  checks, causal paths, and move actions. Do not use filename-based
  resolveTicket/getTicketList to build this diagnostic inventory.
- `src/commands/doctor/instructions.ts`: export
  `Instructions.checkAssets(resourceRoot: string, signal: AbortSignal):
  Promise<DoctorReport>` and
  `Instructions.checkFile(path: string, expectedName: string,
  signal: AbortSignal): Promise<DoctorReport>`. Own frontmatter validation and
  narrowly scoped edits; Installation retains installed-manifest discovery and
  passes owned Markdown instruction candidates to checkFile.
- `src/project-initialization.ts`: share existing init behavior via
  `ProjectInitialization.ensureConfig(projectRoot: string, signal: AbortSignal):
  Promise<void>` and `ensureIgnoreRules(projectRoot: string, signal: AbortSignal):
  Promise<void>`. Own default config and required ignore lines, consumed by init,
  runtime validation and doctor without invoking init as a nested CLI command.
- Existing doctor installation/project modules retain discovery and check
  ownership; project diagnostics incorporate Tickets.check and initialization
  repair actions. Reuse current Markdown parser and Text.slugify conventions.
- Private algorithms, fixture layout, helper names and incidental files remain
  implementation choices within these reviewed API boundaries.

## Representative outcomes

- A discovered project's missing config and incomplete ignore rules are
  repairable. Create the same default config as init; preserve existing config
  content and unrelated ignore rules. Do not initialize a new project outside
  the existing discovery contract or replace invalid existing configuration.
- A valid customized owned SKILL.md passes despite a changed checksum. A wrong
  name offers a narrow name repair; a missing description remains a manual
  finding. Neither case causes instruction regeneration or manifest writes.
- If metadata says id 0042, slug fix-parser, status closed, its expected location
  is `.coderail/tickets/closed/0042-fix-parser.md`. Move/rename from a different
  location only if metadata is valid, identity unique, destination unoccupied,
  and input unchanged. Preserve the ticket bytes, including timestamps.
- For an unfinished `0042 -> 0038 -> 0031 (dismissed)` chain, report the blocker
  and affected tickets with causal context. An ordinary pending chain without
  a blocker does not fail merely for waiting. Do not edit the dependency graph.
- A failed repair does not prevent an independent action. A valid customized
  instruction is still customized after repair because ownership baselines stay
  unchanged. Running doctor again validates content without a checksum-only error.

## Agreed verification expectations

- Preserve plain doctor diagnostics and bootstrap operation with invalid config.
- Cover each agreed repair, preservation of user content, unsupported findings,
  partial failure, cancellation, and idempotence.
- Cover actions deduplicated by key, changed inputs, newly occupied destinations,
  no prompts in non-interactive mode, and no writes during plain diagnostics.
- Verify init and doctor share defaults/ignore rules without changing established
  init behavior. Cover nested cwd and absence of a project.
- Cover asset and owned global/local instruction selection; exclude unowned
  installed instructions from edits. Cover skill and Markdown subagent names,
  strict missing-opener recognition, unsupported delimiter/metadata cases, and
  preservation of body bytes, unrelated fields, BOM and line endings.
- Confirm no ownership manifest/checksum writes; valid customized instruction
  Markdown passes in source and compiled layouts, while binaries and other
  distribution files still receive strict integrity checks.
- Confirm final status reflects the agreed post-repair success contract.
- Ticket fixtures should cover placement/identity/title mismatches, invalid
  closure metadata, missing/ambiguous references, direct/transitive cycles,
  duplicate chains, dismissed blockers, and healthy waiting chains. Continue
  independent checks after malformed/unreadable files, without inventing graph
  conclusions from unavailable metadata.
- Run per-file `cr verify` for any implementation changes under src/tests.

## Readiness

- Outcome, scope, important behavioral contracts, module boundaries, public
  interfaces and verification expectations have been reviewed and agreed.
- No blocking product or architectural decisions remain. Keep a single idea;
  private algorithms, action key encoding, output wording and fixture layout
  remain delegable implementation choices.
- This exploration changes planning artifacts only. Implementation and ticket
  generation are outside this exploration.
